## 2. Slot enum research (Part A) — conclusion: (A) opaque IDs

**Question:** Are `WHOLE | PART_IN_PERCENTAGE | PART_IN_NUMBER | FRACTION | RATIO | RELATIONAL_OPERATOR | UNKNOWN` semantic categories the engine special-cases, or opaque option identifiers?

**Conclusion: (A) — opaque matching keys for runtime behavior.**

Evidence:

1. **Product** (`design-docs/PRODUCT.md` §5 / `PRODUCT_BOOK.md` Layer 3) lists them as *“typed slots such as …”* and says *“The exact slots available are defined by the current problem version”* (PB-005). Pedagogically they name Whole/Part categories for the original curriculum — but availability is problem-version-defined.
2. **Engine** (`packages/engine/src/index.ts`) never branches on a specific slot string; it only equality-compares option `slot` vs step `correct_slot` / workspace occupancy.
3. **AC-036–AC-039** describe EX-01..04 *example journeys*, not hardwired per-slot engine rules. Those examples are now retired on Neon.

**Implication for arithmetic content:** the 7 enum values are reused as **internal option ids**. Students see `options[].label` (e.g. `"19"`), not the slot name. Constraint still in force (`packages/problem-content/src/schema.ts`):

- within a step, option `slot` values must be unique;
- across a problem, each step’s `correct_slot` must be unique  
  → 5 steps need 5 distinct correct slots (fits in the 7-value enum).
